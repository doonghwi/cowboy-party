# 제보 답변 채널 + "방어가 뚫리는 이유" 안내 — 기획서 (2026-11-06)

상태: **승인대기** · 작성: Claude · 결정: 동휘

## 배경
- 2026-11-05 ntfy로 제보 1건: "가끔 방어를 해도 피해지는데 의도된 건가요?" — 보낸 사람 닉네임 **ㅇㅅㅇ**(uid `gfU6NA…`, `nicknames` 공개 노드로 특정).
- 코드 점검 결과 **버그 아님**. 방어가 뚫리는 경우는 설계상 4가지:
  1. 스나이퍼 빵야 20% 관통 (`party_logic.dart` `roll(i,'pierce') < 0.20`)
  2. 슈퍼빵야 (방어 무시)
  3. 러시안룰렛 '운명의 방아쇠' 자해 50% (자기 총이라 못 막음)
  4. 부두술사 저주 만료 턴
- 그런데 **유저가 알 길이 없다**: 게임방법의 방어 설명은 "슈퍼빵야만 못 막아요"라고만 적혀 있고, 관통은 **쏜 사람** 자리에 작은 '관통!' 배지만 떠서 맞은 사람은 못 본다.
- 제보는 앱 → ntfy 한 방향이라 **답을 돌려줄 길이 없다**. 공지(`announcements.dart`)도 앱에 박혀 있어 공지 한 줄 바꾸려면 앱 업데이트가 필요하다.

## 목표
1. 이번 제보자(ㅇㅅㅇ)에게 답이 닿는다.
2. 앞으로 어떤 제보든 **앱 업데이트 없이** 1:1 답변·전체 공지를 보낼 수 있다.
3. 방어가 뚫린 판에서 **맞은 사람 화면에 이유가 보인다** → 같은 제보 재발 방지.

## 사용자
- 플레이어: 제보 보낸 뒤 답을 받고 싶다. 죽었을 때 왜 죽었는지 알고 싶다.
- 운영자(동휘·Claude): 제보를 보고 한 줄로 답하고 싶다. 공지도 바로 띄우고 싶다.

## 요구사항

### A. 제보 저장 + 1:1 답변 (서버: Firebase RTDB)
- 데이터: `feedback/{uid}/{pushId} = { text, at, build, reply?, repliedAt?, readAt? }`
- 보내기: 앱이 **RTDB에 저장 + 기존 ntfy 전송 둘 다**(ntfy는 동휘 알림용, 본문에 `[#uid6]` 유지). RTDB 저장 실패해도 ntfy는 보냄(베스트에포트).
- 보기: 설정 → '관리자에게 제보·문의' 창이 **내 제보 목록 + 운영자 답변**을 보여줌(최근 20건). 답변이 새로 달리면(`reply` 있고 `readAt` 없음) 설정 버튼·메뉴에 **빨간 점**, 창을 열면 `readAt` 기록.
- 규칙(`database.rules.json`): `feedback/$uid` 는 **본인만 읽기**, `text/at/build/readAt`만 본인 쓰기(text ≤ 500자). `reply/repliedAt`는 클라이언트 쓰기 금지 → 관리자만.
- 관리자 답변 도구: `tools/feedback_reply.py` — `firebase database:update`(이 맥의 Firebase CLI 로그인 = 관리자 권한, **새 키 불필요**)로 `reply/repliedAt` 기록. 사용법: `python3 tools/feedback_reply.py list` (답 없는 제보 목록, 닉네임 함께) / `python3 tools/feedback_reply.py reply <uid앞6> "<답변>"`. Claude에게 "ㅇㅅㅇ에게 ~라고 답해줘"라고 하면 Claude가 실행.
- 게스트(익명 로그인)도 uid가 있으므로 동일하게 동작. 로그아웃·계정 삭제 시 `feedback/{uid}`는 계정 삭제 흐름에 포함해 같이 지움.

### B. 원격 공지 (서버: RTDB `notices/`)
- 데이터: `notices/{pushId} = { date, title, body, until? }` (`.read: true`, 쓰기는 관리자만).
- 앱: 시작 시 `notices`를 읽어 **내장 공지 목록 앞에 합쳐** 배너·공지 화면에 표시(날짜 내림차순). 네트워크 실패면 내장 목록만.
- 관리자 도구: `tools/notice.py post "<제목>" "<본문>"` / `list` / `remove <id>`.
- 첫 공지(이번에 올릴 것): **"🛡️ 방어가 안 먹힌 것 같나요?"** — 4가지 경우를 사용자 말투로.

### C. 사망 원인 표시 (앱)
- 맞은 사람 좌석 배지(`circular_table._fxLabel`)에 **피격 쪽 라벨** 추가: 관통당함 → `'관통당함!'`, 슈퍼빵야 피격 → `'슈퍼빵야!'`, 룰렛 자해 → 기존 `'꽝!'` 유지, 저주 → 기존 `'저주 사망!'` 유지.
- 내 좌석이 죽은 턴에는 화면 하단 한 줄 안내: "스나이퍼의 관통에 맞았어요 (방어 20% 관통)" 등 4종 문구. 온라인·오프라인 모두.
- 엔진 산출 추가: `PartyOutcome`에 `piercedBy`(좌석별 관통 피격 여부)·`superHitBy`. 판정 로직은 **변경 없음**(표시만).

### D. 설명 보강 (앱)
- 게임방법 '방어' 항목: "단, 슈퍼빵야는 못 막아요" → "못 막는 것: 슈퍼빵야 · 스나이퍼의 관통(20%) · 저주 만료 · 룰렛 자해".
- `char_core.dart` 주석 10% → 20%로 정정(코드·카드 모두 20%, 주석만 틀림).

### E. 이번 제보자 답변
- 기능 배포 전에는 답을 전할 길이 없으므로 **배포 후** `feedback_reply.py`로 ㅇㅅㅇ에게 답변. 단 ㅇㅅㅇ의 원 제보는 RTDB에 없음(배포 전 제보) → 관리자 도구가 **제보 없이도 답변 생성 가능**해야 함(`reply`만 있는 항목 = "운영자 메시지"로 표시).

## 범위 밖
- 제보에 대한 사용자의 재답장(대화 스레드) — 1차는 한 번 답하면 끝. 더 궁금하면 새 제보.
- 푸시 알림 — 앱을 열었을 때 빨간 점으로만 알림.
- 관리자 화면을 앱 안에 넣는 것 — CLI 도구로 충분(동휘는 Claude에게 말로 시킴).
- 판정 규칙 변경(관통 확률 등) — 이번엔 표시·안내만.

## 확인 방법
- 에뮬 debug 빌드: 제보 보내기 → RTDB `feedback/{uid}`에 저장 확인 → `feedback_reply.py reply` → 앱 재진입 시 설정에 빨간 점 → 창 열면 답변 보이고 점 사라짐.
- `notice.py post` → 앱 재시작 시 공지 배너 맨 위에 뜸. 네트워크 끊고 실행해도 앱이 내장 공지로 정상.
- 오프라인 대전에서 스나이퍼 봇 상대로 방어 반복 → 관통당한 턴에 '관통당함!' 배지 + 하단 문구. 슈퍼빵야·저주·룰렛 각 1회 확인(테스트로 엔진 산출 검증, 화면은 스크린샷).
- 규칙: 다른 uid로 `feedback/{남의uid}` 읽기 → 거부, 클라이언트로 `reply` 쓰기 → 거부(REST로 검증).
- `flutter analyze` 0, 기존 테스트 264 통과 + 엔진 산출 테스트 추가.

2. 공지 데이터 구조를 바꾸면서 **내장 공지도 서버로 옮길지** — 기획안: 내장은 그대로 두고 새 공지만 서버(과거 공지 이관은 안 함).

## 개발 순서
1. 엔진 산출(`piercedBy`/`superHitBy`) + 테스트 → C 라벨·문구 → D 설명 (앱만, 서버 무관)

4. B 원격 공지 읽기 + 관리자 도구 2종(`feedback_reply.py`, `notice.py`)
5. 에뮬 E2E(확인 방법대로) → 빌드 36 → Android 업로드(+iOS는 결정 3에 따라)
6. 배포 후: 첫 공지 게시 + ㅇㅅㅇ에게 답변 + announcements.dart 한 줄 + ARCHITECTURE/HANDOFF 갱신
